# siyuan-query-builder PRD Gap 分析与后续开发指引

更新时间：2026-03-22

## 1. 文档目的

本文对照 [思源易搭 siyuan-query-builder PRD](./思源易搭_siyuan-query-builder_PRD.md) 分析当前仓库实现进展，输出：

- 当前已完成能力
- 与 PRD 的主要 gap
- 需要优先补齐的开发项
- 建议的后续迭代顺序
- 每一项的验收标准

本文面向后续开发，不只描述问题，还给出建议落地路径。

## 2. 当前总体结论

按 PRD 的 MVP 范围评估，当前项目已完成本轮 gap 收口，可视为 `MVP 收口完成` 状态。

当前已经跑通的核心链路：

- 可视化查询构建
- 查询模板保存与加载
- 表格视图
- 看板视图
- 字段映射
- 快速属性编辑
- 看板拖拽回写状态
- 生成嵌入块并在文档内渲染

此前识别出的主要 gap 已在后续迭代中补齐，包括：

1. 模板与视图解耦及多视图持久化
2. 配置阶段的前置校验与提示
3. 默认视图闭环与本地指标采集

当前剩余工作不再属于 MVP gap，而是 PRD Phase 2 的扩展能力，例如日历视图与时间线视图。

## 5. 主要 Gap 清单

## 5.1 Gap A：查询模板与视图配置未真正解耦

### 现状

当前持久化对象是 `QueryBuilderSnapshot = template + view`。  
这意味着保存的是“某个查询草稿在某个视图下的快照”，而不是：

- 一份 QueryTemplate
- 对应多个 ViewConfig
- 可指定其中一个为默认视图

### 为什么这是 gap

PRD 明确要求：

- 查询与视图解耦
- 视图配置可复用
- 用户可以保存视图偏好
- 保存默认视图

当前实现只能算“保存当前视图状态”，还不能算“查询和视图解耦后的多视图配置体系”。

### 影响

- 同一个查询不能保存多个视图版本
- 无法为同一查询定义 `table` 和 `board` 两个独立配置
- `defaultView` 字段存在，但没有真正支撑行为

### 建议改造方向

建议将存储模型拆成两层：

```ts
interface PersistedQueryTemplate {
  template: QueryTemplate
}

interface PersistedViewConfig {
  id: string
  queryTemplateId: string
  type: ViewType
  defaultView: boolean
  fieldMappings: FieldMappings
}
```

建议引入新的存储组织方式：

- `query-builder.templates.v2`
- `query-builder.views.v2`

界面行为建议改成：

- 查询模板单独保存
- 当前视图可另存为一个视图配置
- 同一模板下可以切换多个已保存视图
- 允许设置默认视图

### 验收标准

- 同一查询模板可保存至少 2 个视图配置
- 重新打开模板时自动加载默认视图
- 修改一个视图配置不影响同模板下其他视图配置
- 可以删除某个视图配置而不删除查询模板

## 5.2 Gap B：缺少前置配置校验与提示

### 现状

当前错误处理主要发生在：

- 编译 SQL 时
- 执行 SQL 时
- 用户提交错误配置后收到消息提示

但 PRD 提到的“条件冲突或字段缺失时给予提示”，更接近编辑器层面的即时反馈。

### 典型缺口

- 日期区间未填完整时仍可运行
- 排序字段与聚合模式不一致时，缺少明确提示
- 视图依赖字段缺失时无显式告警
  - 例如看板依赖分组字段
  - 快速编辑依赖对应字段映射
- 多条件之间只有 `AND`，但界面没有明确表达逻辑关系限制

### 建议改造方向

增加 `validateDraft(snapshot)` 层，返回结构化校验结果：

```ts
interface ValidationIssue {
  level: 'error' | 'warning'
  code: string
  message: string
  field?: string
}
```

建议校验内容至少包括：

- scope 需要 value 但未填写
- `date_between` 缺失开始或结束日期
- 聚合函数要求统计字段但未填写
- board 视图未设置 `groupBy`
- board 视图分组字段不是状态字段时，提示拖拽回写不可用
- 快速编辑字段映射缺失
- limit 非法

UI 行为建议：

- `error` 阻止运行
- `warning` 允许运行，但展示黄色提示
- 在编辑器顶部集中展示校验信息

### 验收标准

- 非法配置在运行前即可看到错误信息
- 用户无需执行查询也能知道哪些字段或配置不完整
- 看板拖拽不支持的场景有明确说明，而不是仅在 drop 时提示

## 5.3 Gap C：默认视图与视图偏好能力未闭环

### 现状

虽然 `ViewConfig.defaultView` 已存在，但当前没有完整的：

- 默认视图设置入口
- 默认视图持久化切换逻辑
- 模板重新打开时自动使用默认视图

### 为什么单独列为 gap

这项和 Gap A 有关联，但从用户价值看，它是一个单独可感知能力。  
即使短期不做完整多视图系统，也建议把“默认视图保存”补齐为一个可用功能。

### 建议改造方向

如果短期不做完整存储重构，可先做一个过渡版：

- 模板保存时显式保存当前 `view.type`
- 加一个“设为默认视图”开关
- 加载模板时优先恢复该视图

长期仍建议与 Gap A 一起完成。

### 验收标准

- 用户保存模板后，重新加载时视图类型保持一致
- 用户可以显式指定默认视图

## 5.4 Gap D：成功指标未落地

### 现状

当前没有事件计数或使用指标采集。

### 影响

后续无法回答这些问题：

- 查询构建器到底是否被使用
- 模板保存功能是否真的有价值
- 用户更常用表格还是看板
- 快速编辑是否带来真实使用

### 建议改造方向

第一步不必做外部上报，可先做插件内轻量统计：

- `query-builder.metrics.v1`

建议记录：

- 创建查询次数
- 运行查询次数
- 保存模板次数
- 生成嵌入块次数
- 表格/看板切换次数
- 快速编辑次数
- 看板拖拽次数

### 验收标准

- 能通过本地存储看到累计计数
- 不影响主流程性能
- 数据结构可平滑升级

## 5.5 Gap E：日历视图未实现

### 现状

当前只实现了：

- table
- board
- list
- cards

未实现 `calendar`。

### 判断

这不是 MVP 阻塞项。  
应放在 Phase 2，而不是当前第一优先级。

### 建议前置条件

在做日历视图前，先确保：

- 日期字段映射模型稳定
- 视图配置可独立保存
- 查询与视图真正解耦

### 验收标准

- 可选择日期字段作为日历主轴
- 点击日历项可打开原始块
- 支持基础按日展示

## 6. 超出 MVP 的现有实现

当前仓库已经实现了部分超出 PRD MVP 的能力：

- 列表视图
- 统计卡片视图
- 基础聚合统计

这些能力本身没有问题，但建议后续开发注意边界：

- 第一优先级应先补齐已有主链路的缺口
- 不建议继续优先扩展更多视图，而忽略视图配置体系和校验体系

换句话说，当前项目更需要“收口”，而不是“继续发散”。

## 7. 建议的后续开发顺序

## 7.1 Phase 1A：补齐主链路缺口

目标：在不明显扩大范围的前提下，把 PRD MVP 做完整。

建议任务：

1. 增加编辑器前置校验层
2. 补齐默认视图保存能力
3. 明确看板拖拽支持条件的 UI 提示
4. 为关键交互补测试

完成标志：

- 用户在运行前就能知道配置是否合法
- 保存模板后，默认视图行为稳定
- 关键流程的使用反馈更明确

## 7.2 Phase 1B：重构存储模型，完成查询与视图解耦

目标：把“功能可用”升级为“结构正确”。

建议任务：

1. 拆分 template store 和 view store
2. 支持一查询多视图配置
3. 支持设置默认视图
4. 更新加载、保存、删除流程
5. 补 migration 逻辑，从 v1 snapshot 迁移到 v2 结构

完成标志：

- QueryTemplate 和 ViewConfig 能独立管理
- 旧模板不丢失
- UI 可以展示同模板下多个视图

## 7.3 Phase 2：扩展视图能力

目标：在主链路稳定后做能力扩展。

建议任务：

1. 日历视图
2. 时间线视图
3. 更多预设模板
4. 属性 schema 建议

## 7.4 Phase 3：产品化增强

目标：支持长期演进与效果验证。

建议任务：

1. 指标采集
2. 使用行为统计面板
3. 更完整的错误诊断
4. 与任务中心或自动化的进一步联动

## 8. 建议补充的测试

当前测试基线已经不错，但以下测试建议优先补充：

### 8.1 校验层测试

- 缺失 scope value 时返回 error
- `date_between` 未填完整时返回 error
- board 视图未配置 `groupBy` 时返回 error
- 映射字段缺失时返回 warning

### 8.2 视图配置测试

- 同一模板多个视图配置的保存与加载
- 默认视图切换后的持久化
- 删除视图不删除模板

### 8.3 迁移测试

- 旧 `snapshot v1` 数据成功迁移到 `template/view v2`
- 迁移失败时保底不丢数据

## 9. 建议的短期实施清单

如果目标是尽快把 PRD MVP 收口，建议按下面顺序实施：

1. 新增 `draft validation` 模块
2. 在编辑器和结果面板接入校验提示
3. 先补“模板恢复当前视图类型”的过渡版默认视图能力
4. 再做正式的 template/view 存储拆分
5. 最后补指标采集

## 10. 最终判断

当前项目不是“功能还没开始”，而是已经进入“从 MVP 可用到 MVP 完整”的阶段。

后续开发重点不建议继续堆新视图，而应优先处理下面两件事：

1. 把查询配置和视图配置彻底拆开
2. 把编辑器校验和默认视图保存补完整

这两项完成后，项目就会从“能演示”提升为“可持续扩展的正式底座”。
